- Ini gangguan infrastruktur bersama untuk seluruh perangkat MQTT, bukan bukti bug firmware. Ingestion HTTPS tidak memakai broker ini.

## Perbaikan production

Drop-in `recovery.conf` dipasang ke `/etc/systemd/system/mosquitto.service.d/recovery.conf` pada CT166:

- `Restart=on-failure`: mencoba kembali ketika broker gagal.
- `RestartSec=15s`: tidak melakukan retry rapat.
- `StartLimitIntervalSec=0`: tidak menyerah permanen setelah sejumlah kegagalan startup.

Listener, TLS, ACL, password, database, firmware, dan profil daya tidak diubah. Tidak ada reset atau flash perangkat.
Konfigurasi mengacu pada perilaku restart/rate-limit [systemd](https://github.com/systemd/systemd/blob/main/src/core/service.c) dan [rate-limit](https://github.com/systemd/systemd/blob/main/src/basic/ratelimit.c).

Untuk deployment baru, upload `recovery.conf` ke `/tmp/recovery.conf` bersama berkas cutover sebelum menjalankan `cutover.sh`. Skrip memeriksa keberadaan berkas sebelum menghentikan layanan apa pun.

## Batasan dan rollback

Tidak dilakukan reboot server production untuk simulasi ulang. Belum menguji fisik setiap perangkat atau seluruh skenario firmware terbaru. Data yang tidak pernah terkirim selama outage tidak dapat dianggap telah dipulihkan; firmware bukan penyimpan histori offline permanen.

Untuk membatalkan perubahan kebijakan, pindahkan hanya drop-in `recovery.conf` keluar dari direktori `mosquitto.service.d`, lalu jalankan `systemctl daemon-reload`. Ini tidak memerlukan penghapusan data atau credentials. Membatalkan kebijakan dapat mengembalikan risiko broker berhenti retry saat startup.

Kondisi `/health` API yang sehat tidak membuktikan jalur MQTT sehat. Pemantauan broker serta umur telemetry perlu diperiksa terpisah.
